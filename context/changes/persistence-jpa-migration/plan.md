# Migrate persistence to JPA / Hibernate + rename persistence types — Implementation Plan

## Overview

Replace **Spring Data JDBC** with **Spring Data JPA / Hibernate** in
`infrastructure/persistence`, and in the same pass rename the seven persistence types
into clear role-named classes with the two data holders moved to a `persistence/entity/`
subpackage.

Nothing above the persistence adapters changes: the `domain` aggregates stay framework-free
records, the `application` ports keep their exact signatures, `CouponService` keeps its
manual `TransactionTemplate` boundary, the REST layer is untouched, and the Liquibase
schema is unchanged. The migration is **behaviour-neutral**, and the existing Testcontainers
integration tests — `RedemptionConcurrencyIT` above all — are the proof.

## Current State Analysis

- **Persistence package** (`src/main/java/com/example/coupons/infrastructure/persistence/`),
  7 flat package-private types:
  - `CouponRow` / `CouponRedemptionRow` — Spring Data JDBC `@Table` records (persistence model).
  - `CouponCrudRepository` / `CouponRedemptionCrudRepository` — `CrudRepository` interfaces;
    the coupon one adds `findByCode` and the atomic `@Modifying @Query`
    `UPDATE coupon SET current_uses = current_uses + 1 WHERE id = :id AND current_uses < max_uses`
    returning `int` rows-affected.
  - `CouponJdbcRepository` / `CouponRedemptionJdbcRepository` — `@Repository` adapters
    implementing the `application.port` interfaces; map row↔domain and translate a
    unique-constraint violation into `DuplicateCouponCodeException` / `AlreadyRedeemedException`.
  - `PersistenceExceptions` — walks the cause chain for `DuplicateKeyException` or a
    `SQLException` with SQLSTATE `23505`.
- **Ports** (`application/port/`): `CouponRepository` (`save`, `findByCode`,
  `incrementUsageIfBelowLimit`), `CouponRedemptionRepository` (`insert`). Unchanged by this plan.
- **`CouponService`** owns the only transaction boundary — a `TransactionTemplate`
  at `ISOLATION_READ_COMMITTED`. `registerRedemption` (`CouponService.java:97-108`) does:
  `redemptionRepository.insert(...)` → `couponRepository.incrementUsageIfBelowLimit(...)`
  → `couponRepository.findByCode(...)` **inside the same transaction** to read back the
  new `remainingUses`.
- **Schema** — Liquibase, 2 changesets, IDs `BIGINT GENERATED BY DEFAULT AS IDENTITY`,
  `code` / `country` / `resolved_country` are `VARCHAR`/`CHAR(2)`, timestamps
  `TIMESTAMP WITH TIME ZONE`. `UNIQUE (code)` = `uq_coupon_code`,
  `UNIQUE (coupon_id, user_id)` = `uq_redemption_coupon_user`.
- **`build.gradle` — none**; Maven, `spring-boot-starter-parent` 3.3.5, Java 21.
  `spring-boot-starter-data-jdbc` + `postgresql` + `liquibase-core` on the persistence side.
- **`ArchitectureTest`** (ArchUnit): `the_domain_is_pure` already forbids
  `jakarta.persistence..` inside `..domain..`; `respects_layering` seals
  `..infrastructure.persistence..` (trailing `..` ⇒ **includes any subpackage**) so a new
  `persistence.entity` package needs no rule change.
- **Tests**: `CouponServiceTest` (Mockito, mocks the ports — no Spring), 5 `*IT`
  classes on `@SpringBootTest` + `@ActiveProfiles("test")` + `TestcontainersConfiguration`
  (real Postgres 16, real Liquibase). `RedemptionConcurrencyIT` asserts exactly 20 of 100
  parallel racers succeed with zero counter drift. `application-test.yml` inherits from
  `application.yml`, adding only Hikari pool size and geoip overrides.
- Grep-confirmed: **no type outside `infrastructure/persistence/` names any of the 7 types.**

## Desired End State

- `infrastructure/persistence/` runs on Hibernate via Spring Data JPA:
  ```
  infrastructure/persistence/
  ├── entity/
  │   ├── CouponEntity.java              @Entity @Table(name = "coupon")
  │   └── CouponRedemptionEntity.java    @Entity @Table(name = "coupon_redemption")
  ├── CouponJpaRepository.java           extends JpaRepository<CouponEntity, Long>
  ├── CouponRedemptionJpaRepository.java extends JpaRepository<CouponRedemptionEntity, Long>
  ├── CouponPersistenceAdapter.java      implements CouponRepository        (@Repository)
  ├── CouponRedemptionPersistenceAdapter.java  implements CouponRedemptionRepository
  └── UniqueViolations.java              (was PersistenceExceptions)
  ```
- `spring-boot-starter-data-jpa` replaces `spring-boot-starter-data-jdbc`; Lombok added
  (`optional` scope, version managed by the Boot parent).
- `application.yml` sets `spring.jpa.hibernate.ddl-auto: validate` and
  `spring.jpa.open-in-view: false`. Liquibase still builds the schema; Hibernate only
  validates its mappings against it at startup.
- The usage-cap guarantee is unchanged — a single atomic conditional bulk `UPDATE`.
- `./mvnw clean verify` is green: `CouponServiceTest` unmodified, all 5 ITs pass,
  `ArchitectureTest` green, Hibernate `validate` passes during IT context startup.
- README and code comments no longer say "Spring Data JDBC" / "Jdbc".

### Key Discoveries

- The atomic increment is the assignment's core guarantee
  (`CouponCrudRepository.java:13-20`, `RedemptionConcurrencyIT.java:25-31`). It must stay a
  DB-side conditional `UPDATE`; JPA offers `@Modifying` bulk update for exactly this.
- **`CouponService.java:105`** re-reads the coupon in the same transaction. A JPA bulk
  update bypasses the persistence context, so without `clearAutomatically = true` the
  read-back returns the **stale pre-increment** entity from the L1 cache.
- **`CouponServiceTest.java:77-86`** requires `redemptionRepository.insert(...)` to throw
  `AlreadyRedeemedException` synchronously (it asserts `incrementUsageIfBelowLimit` is
  *never* called after). With JPA, a bare `save()` on a new entity may not touch the DB
  until flush/commit — the adapter must `saveAndFlush` so the unique violation is raised
  *inside* its own try/catch. Same reasoning for `CouponPersistenceAdapter.save`
  (`CouponApiIT` "duplicate code → 409").
- `GenerationType.IDENTITY` also forces an immediate INSERT on `persist`, so `saveAndFlush`
  is belt-and-braces here, not the sole safeguard — but it makes the contract explicit.
- Hibernate surfaces a unique violation as `org.hibernate.exception.ConstraintViolationException`,
  which the Spring Data `@Repository` proxy translates to
  `org.springframework.dao.DataIntegrityViolationException`. `UniqueViolations` must
  recognise those in addition to the current `DuplicateKeyException` / SQLSTATE `23505` check.
- Spring Boot's default physical naming strategy maps `createdAt → created_at`,
  `maxUses → max_uses`, etc. — so no `@Column` names are needed; `ddl-auto: validate`
  will confirm this at first IT startup.
- `JdbcTemplate` (used by `RedemptionConcurrencyIT.java:40` and the README ops snippets)
  stays auto-configured — `spring-boot-starter-jdbc` is transitive via `-data-jpa`.

## What We're NOT Doing

- **Not** touching `domain`, `application` (ports, `CouponService`, DTOs), `api`, or
  `infrastructure/{web,geoip}`.
- **Not** changing the port interfaces or their signatures.
- **Not** changing the transaction boundary, isolation level, or the `TransactionTemplate`
  in `CouponService`.
- **Not** changing the Liquibase schema — no new columns, no `@Version` / optimistic-lock
  column, no `hbm2ddl` schema generation.
- **Not** adding `@Version` optimistic locking or pessimistic (`SELECT … FOR UPDATE`)
  locking — the conditional `UPDATE` strategy is kept as-is.
- **Not** adding new test classes or slices (`@DataJpaTest`) — the existing ITs are the
  acceptance gate. (Lean-testing bar: one check per behaviour.)
- **Not** running Spring Data JDBC and JPA side by side — full starter replacement.
- **Not** introducing Lombok anywhere outside the two `@Entity` classes.

## Implementation Approach

Two phases. **Phase 1** does the whole migration — build, config, and all seven
persistence types with their final names — verified end-to-end by `./mvnw clean verify`.
A persistence-adapter swap can't be half-applied while compiling, so the code changes land
together and the IT suite is what proves correctness. **Phase 2** is the documentation and
comment sweep, plus an ArchUnit re-confirm.

Rollback is a single `git revert` of the Phase 1 commit — no data or schema migration is
involved.

## Critical Implementation Details

- **Persistence-context coherence around the increment.** The `@Modifying` bulk update on
  `CouponJpaRepository` must carry `clearAutomatically = true` (so `CouponService.java:105`'s
  same-transaction read-back sees the new `current_uses`) and `flushAutomatically = true`
  (so any pending insert is flushed before the update runs). Without `clearAutomatically`
  the concurrency IT and the `RedemptionResult.remainingUses` in every redemption response
  are silently wrong.
- **Synchronous unique-violation detection.** Both adapters must use `saveAndFlush(...)`,
  not `save(...)`, so the DB constraint fires inside the adapter's `try/catch` and is
  translated to the domain exception there — `CouponServiceTest.java:77` and the
  `*ApiIT` 409 cases depend on it.
- **Do not put `@Data` or `@EqualsAndHashCode` on the entities.** Lombok `@Data` generates
  `equals`/`hashCode` over mutable fields (incl. a null-then-assigned `@GeneratedValue` id),
  a well-known JPA footgun. Use only `@Getter @Setter @NoArgsConstructor(access = PROTECTED)
  @AllArgsConstructor`; identity `equals` is correct here.
- **Ordering within Phase 1.** Land the `pom.xml` change, then the `entity/` classes, then
  the repositories, then the adapters, then delete the old `*Row` files and rename
  `PersistenceExceptions` — the module will not compile until the set is complete; that is
  expected and the phase's automated verification covers it.

## Phase 1: JPA / Hibernate migration

### Overview

Swap the starter, add JPA config, and rewrite all seven persistence types with their
final names and the `persistence/entity/` subpackage. Behaviour-neutral; verified by the
full test suite.

### Changes Required:

#### 1. Build — starter swap + Lombok

**File**: `pom.xml`

**Intent**: Move from Spring Data JDBC to Spring Data JPA / Hibernate, and make Lombok
available for the two entity classes.

**Contract**: In `<dependencies>`, replace the
`org.springframework.boot:spring-boot-starter-data-jdbc` entry with
`org.springframework.boot:spring-boot-starter-data-jpa`. Keep `postgresql` (runtime) and
`liquibase-core` unchanged. Add:

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>
```

Version is managed by `spring-boot-starter-parent`; the parent already excludes Lombok
from the repackaged jar. No `maven-compiler-plugin` change is needed (annotation processor
is auto-discovered from the classpath).

#### 2. JPA configuration

**File**: `src/main/resources/application.yml`

**Intent**: Let Liquibase keep ownership of the schema while Hibernate validates its
mappings; disable Open Session In View.

**Contract**: Add under `spring:`

```yaml
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
```

`application-test.yml` and `application-dev.yml` inherit this — no change to either.
(Optional, not required: `spring.jpa.properties.hibernate.jdbc.time_zone: UTC` for
timestamp determinism; omit unless an IT shows a drift.)

#### 3. Coupon entity

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/entity/CouponEntity.java` (new; replaces `../CouponRow.java`)

**Intent**: JPA mapping for the `coupon` table. Mutable-by-Hibernate data holder,
constructed all-args by the adapter, read via getters.

**Contract**: `public class CouponEntity` in package
`com.example.coupons.infrastructure.persistence.entity`.
Annotations: `@Entity`, `@Table(name = "coupon")` (both `jakarta.persistence`),
`@Getter @Setter @NoArgsConstructor(access = AccessLevel.PROTECTED) @AllArgsConstructor`
(Lombok). Fields, in this order for the all-args constructor:
`@Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id`,
`String code`, `Instant createdAt`, `int maxUses`, `int currentUses`, `String country`.
No `@Column` overrides — rely on the snake_case naming strategy. **No `@Data`,
no `@EqualsAndHashCode`.**

#### 4. Redemption entity

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/entity/CouponRedemptionEntity.java` (new; replaces `../CouponRedemptionRow.java`)

**Intent**: JPA mapping for the `coupon_redemption` table.

**Contract**: Same annotation set and constructor conventions as `CouponEntity`.
`@Table(name = "coupon_redemption")`. Fields:
`@Id @GeneratedValue(strategy = GenerationType.IDENTITY) Long id`,
`Long couponId`, `String userId`, `Instant redeemedAt`, `String resolvedCountry`.
The `coupon_id` FK is modelled as a plain `Long` (no `@ManyToOne`) — matches the current
row shape and the port contract, and keeps the aggregate boundary.

#### 5. Coupon Spring Data repository

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/CouponJpaRepository.java` (renamed from `CouponCrudRepository.java`)

**Intent**: Spring Data JPA interface over `CouponEntity`: derived `findByCode`, plus the
atomic conditional usage-increment.

**Contract**: `interface CouponJpaRepository extends JpaRepository<CouponEntity, Long>`
(package-private). Methods:
- `Optional<CouponEntity> findByCode(String code)` — derived query, unchanged semantics.
- The increment as a JPQL bulk update:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("""
        UPDATE CouponEntity c
           SET c.currentUses = c.currentUses + 1
         WHERE c.id = :id
           AND c.currentUses < c.maxUses
        """)
int incrementUsageIfBelowLimit(@Param("id") long couponId);
```

Returns rows-affected (`0` ⇒ cap reached), exactly as today. (A `nativeQuery = true`
variant against `coupon` / `current_uses` / `max_uses` is an acceptable fallback if the
JPQL form ever misbehaves; the flush/clear flags are the load-bearing part.)

#### 6. Redemption Spring Data repository

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/CouponRedemptionJpaRepository.java` (renamed from `CouponRedemptionCrudRepository.java`)

**Intent**: Spring Data JPA interface over `CouponRedemptionEntity`.

**Contract**: `interface CouponRedemptionJpaRepository extends JpaRepository<CouponRedemptionEntity, Long>`
(package-private). No extra methods.

#### 7. Coupon persistence adapter

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/CouponPersistenceAdapter.java` (renamed from `CouponJdbcRepository.java`)

**Intent**: Implement the `CouponRepository` port against `CouponJpaRepository`; map
entity↔domain; translate a unique-code violation.

**Contract**: `@Repository class CouponPersistenceAdapter implements CouponRepository`,
constructor-injected `CouponJpaRepository`. Behaviour per method:
- `save(Coupon)` — build a `CouponEntity` from the domain object (id `null` for a new
  aggregate), `jpa.saveAndFlush(entity)`, map the result back to `Coupon`. Catch
  `RuntimeException`; if `UniqueViolations.isUniqueViolation(ex)` throw
  `new DuplicateCouponCodeException(coupon.code().value())`, else rethrow.
- `findByCode(CouponCode)` — `jpa.findByCode(code.value()).map(this::toDomain)`.
- `incrementUsageIfBelowLimit(long)` — delegate straight to `jpa`.
- Private `toEntity` / `toDomain` mirroring the current `toNewRow` / `toDomain` in
  `CouponJdbcRepository.java:43-62` (null-safe `country`).

#### 8. Redemption persistence adapter

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/CouponRedemptionPersistenceAdapter.java` (renamed from `CouponRedemptionJdbcRepository.java`)

**Intent**: Implement `CouponRedemptionRepository.insert`; translate the
`(coupon_id, user_id)` unique violation.

**Contract**: `@Repository class CouponRedemptionPersistenceAdapter implements CouponRedemptionRepository`.
`insert(CouponRedemption)` — build a `CouponRedemptionEntity` (id `null`), `jpa.saveAndFlush(entity)`.
Catch `RuntimeException`; if `UniqueViolations.isUniqueViolation(ex)` throw
`new AlreadyRedeemedException(redemption.couponId(), redemption.userId())`, else rethrow.

#### 9. Unique-violation helper

**File**: `src/main/java/com/example/coupons/infrastructure/persistence/UniqueViolations.java` (renamed from `PersistenceExceptions.java`)

**Intent**: Keep a single place that decides "this exception is a unique-constraint
violation", now also covering the Hibernate / Spring-DAO exception shapes.

**Contract**: `final class UniqueViolations` with
`static boolean isUniqueViolation(Throwable ex)`. Walk the cause chain (as today) and
return `true` on any of:
- `org.springframework.dao.DuplicateKeyException` (current check, keep),
- `org.springframework.dao.DataIntegrityViolationException` **whose cause chain contains**
  a SQLSTATE `23505` `SQLException` or an `org.hibernate.exception.ConstraintViolationException`,
- `org.hibernate.exception.ConstraintViolationException` directly,
- a `java.sql.SQLException` with `getSQLState()` equal to `23505` (current check, keep).

Each adapter performs exactly one insert, so "any unique violation on this call" is
unambiguous — no constraint-name matching needed.

#### 10. Delete the old files

**Files**: `CouponRow.java`, `CouponRedemptionRow.java` (deleted — replaced by `entity/`),
and confirm `CouponCrudRepository.java` / `CouponRedemptionCrudRepository.java` /
`CouponJdbcRepository.java` / `CouponRedemptionJdbcRepository.java` / `PersistenceExceptions.java`
are gone (renamed in steps 5–9).

**Intent**: No stale Spring Data JDBC types left in the package.

**Contract**: `git status` shows exactly the renames + 2 deletions + `entity/` additions
in `infrastructure/persistence/`, plus `pom.xml` and `application.yml`.

## Testing Strategy

### Unit Tests

- `CouponServiceTest` — **unchanged**. It mocks the ports, so it is agnostic to the
  persistence technology; it must still pass byte-for-byte. It is also the guard that the
  adapters raise `AlreadyRedeemedException` synchronously (hence `saveAndFlush`).
- Domain tests, `IpApiGeoIpResolverTest` — unchanged, unaffected.

### Integration Tests

- `RedemptionConcurrencyIT` — the acceptance gate for the concurrency guarantee. Exactly
  `maxUses` successes out of `racers`, `current_uses == maxUses`, redemption row count
  `== maxUses`. Must pass with no change.
- `CouponApiIT` — create (incl. duplicate-code → 409), look-up (case-insensitive).
- `CouponRedemptionApiIT` — redeem happy path, repeat-user → 409 ALREADY_REDEEMED,
  exhausted → 409 USAGE_LIMIT_REACHED.
- `CouponRedemptionCountryIT` — country match/mismatch/undetermined.
- All exercise real Postgres + real Liquibase; Hibernate `validate` runs at each context
  startup and would fail the run on any mapping drift.

### Manual Testing Steps

1. `docker compose up db`; `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev`.
2. Run README "End-to-end walkthrough" steps 1–8; confirm every documented status code.
3. `curl http://localhost:8080/actuator/health` → `UP`.
4. Grep the running-app startup log: Liquibase changesets applied, then Hibernate
   `EntityManagerFactory` init with no `validate` error, no OSIV warning.
5. `docker compose down -v && docker compose up -d db` then restart the app — Liquibase
   rebuilds the schema, Hibernate validates clean.

## Performance Considerations

Negligible. The redemption path is still: one `SELECT by code`, one `INSERT` (flushed),
one conditional `UPDATE`, one `SELECT by code`. Hibernate adds a persistence context per
transaction (already short-lived, bounded by `TransactionTemplate`) and `open-in-view:
false` keeps it from leaking into the request thread. `GenerationType.IDENTITY` disables
JDBC insert batching, but each transaction inserts at most one row so there is nothing to
batch.

## Migration Notes

No data migration. No schema change. Rollback = `git revert` of the Phase 1 commit
(Phase 2 is docs-only). The Liquibase changelog and the `databasechangelog` table are
untouched, so a revert needs no DB action.
